我的任務很普通：把收到的資料更新到一個老舊 WordPress 網站。

真正開始操作後，事情卻不只是登入後台、改字、按下更新。有些內容能從 REST 讀取，
但寫入仍得經過瀏覽器；有些公開檔案留在另一套 FTP 結構；後台還混著不同年代的編輯器
與外掛。畫面上看起來是同一個網站，底下其實有好幾種介面。

這是一份規模很小的公部門打工。本文不公開單位、工作場域、實際更新內容、檔名、
內部網址，也不說明需求如何交到我手上。能公開的是我處理這類行政工作的方式：
如何讓 AI 幫我摸清系統，留下可重跑的操作方法，再驗證網站真的改對了。

## AI 先幫我畫出操作邊界

我沒有先做一支包辦所有事情的腳本。第一步是讓 AI 跟著實際任務偵察：

- 公開 REST 能讀到什麼；
- 哪些寫入一定要登入瀏覽器；
- 哪些靜態檔案只能經過 FTP；
- 更新後，應該回到哪一層確認結果。

這些邊界決定了工具怎麼分工。REST 適合讀公開結構；瀏覽器保留登入狀態，處理後台
操作；FTP 只負責既有的靜態檔案。AI 協助我讀頁面結構、試 selector、比較請求內容，
也把失敗路徑記下來。最後留下來的是一張下次仍看得懂的介面地圖。

## 把一次對話變成下一次能執行的流程

早期操作很像一串臨時對話：打開頁面、找欄位、試一次、發現外掛沒有同步，再換一條
路。問題解掉後，如果只留下聊天紀錄，下一次還是得重新猜。

我把跑通的做法整理成 runbook。每一份都回答幾個實際問題：

1. 這類任務應該走 REST、FTP 還是瀏覽器？
2. 寫入前要檢查哪些輸入？
3. 哪些步驟可以重跑，哪些失敗後必須先清理？
4. 寫入成功後，要去哪裡把結果讀回來比對？

後來，重複部分再被收進 adapter、staging payload 與批次程式。AI 不必每次重新理解
整個網站，只要依照已知邊界補齊輸入、執行固定步驟，遇到例外時停在明確的 checkpoint。

```text
收到資料
  -> 整理成固定欄位
  -> preflight 檢查
  -> 選擇 REST / browser / FTP 路徑
  -> 寫入
  -> 從網站讀回結果
  -> 不一致就停止，不繼續下一筆
```

## 寫入成功不等於任務完成

這套流程最重要的規則是：`No write without roundtrip`。

API 回傳成功、後台出現通知，或 FTP 顯示上傳完成，都只能證明某一層接受了操作。
公開頁面可能還是舊內容，檔案可能被快取，後台外掛也可能把欄位寫到另一個位置。因此，
每次寫入後都要從實際會被讀取的地方再抓一次，核對標題、內容狀態、檔案雜湊或公開頁面。

測試資料也必須放在可辨識的 sandbox，跑完就清掉。登入資訊則留在 repo 外的本機設定，
不進入腳本、runbook 或執行結果。

## 三分鐘是怎麼來的

一份 runbook 記錄了同類流程的時間。第一次摸索花了約 90 分鐘；路徑穩定後，單筆操作
連同最終驗證約 3 分鐘。後續版本的一次實測，單筆純機器執行約 40 秒。批次紀錄也顯示，
retry 與 cleanup 花的時間可能遠高於順利執行本身。

這些數字只描述當時那套流程的執行紀錄。它們沒有對照人工基準，也沒有測量錯誤率，
所以不能推成節省了多少工時或提高多少行政效率。比較確定的是，原本散落在瀏覽器操作、
FTP 路徑與臨時判斷裡的知識，現在有了可以檢查、重跑與交接的形式。

## 人還是要處理的部分

輸入資料是否完整、公開文字怎麼寫、圖片是否適合、日期與分類是否合理，這些判斷沒有
交給批次程式。流程會在這些位置停下來，等人確認後才繼續。

我也沒有把內部資料直接丟給外部模型。AI 主要協助拆解介面、產生與修正操作程式、
整理失敗紀錄，以及把跑通的方法寫成 runbook。網站帳密、工作內容與原始來稿留在原本
的工作環境裡。

這篇先停在工程紀錄。產出變快之後，工時、報酬與組織知道多少，會形成另一組問題；
它們需要不同的證據，也適合另外寫。
